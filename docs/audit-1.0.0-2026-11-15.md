# Проверка Yumi Desktop 1.0.0 — 15 ноября 2026

Основа: `f95c3ea` (`main`, `origin/main`, `v1.0.0`). После `git fetch --tags origin`
удалённая ветка указывает на тот же коммит. Установленное приложение также имеет версию 1.0.0.
Предыдущий опубликованный выпуск — 0.2.6; между ним и 1.0.0 находятся 11 коммитов.

Проверена история из 26 коммитов, включая происхождение проблем до последних выпусков.
Ручная проверка сосредоточена на состоянии туннеля, подписках и миграции ID, горячем переключении,
проверке соединения, службе и её протоколе, выходном адаптере, kill switch, DNS,
режиме местоположения, установке и обновлении. Это аудит кода и автоматических проверок;
реальная работа Linux/macOS и их привилегированные операции на этой Windows-машине не проверялись.

## Подтверждённый случай на работающем приложении

Сделан только запрос `status` к существующей службе и чтение количества записей из профиля.
Ни адреса серверов, ни ссылки подписки, ни пароли в этот отчёт не включены.

- Служба запущена и сообщает `state=connected`, без ошибки, с портом проверки туннеля.
- В профиле есть 536 серверов и одна включённая подписка.
- Выбранный в профиле сервер существует.
- `status.nodeId` работающего туннеля отсутствует среди сохранённых серверов
  и не совпадает с выбранным ID.

Это объясняет скриншот: интерфейс определял сервер только поиском `status.nodeId` в изменяемом
списке подписки. Неудачный поиск одновременно включал «Не выбран», пустой пинг и карточку первого
запуска. Состояние службы и трафик при этом оставались подключёнными.

Воспроизведён путь через ротацию реквизитов: обновление подписки находит сервер с прежним именем,
переносит выбор на его новый ID и удаляет прежнюю запись. Служба продолжает обслуживать прежний
outbound со старым ID. Точное историческое событие, которое изменило ID на этой машине,
по одному текущему снимку установить нельзя.

## Исправлено в рабочей копии

### 1. Активный сервер больше не зависит от текущей подписки — P1

Истоки: `53adcbf`; частичное исправление `bec8c76` сохраняло только выбранную строку при её
полном исчезновении и не закрывало ротацию реквизитов или миграцию ID.

`DesktopModel` сохраняет подтверждённую службой запись сервера отдельно, в
`active-connection.json`, вместе с ID службы и началом сеанса. Она переживает обновление подписки
и перезапуск окна; снимок другого сеанса не подставляется. При миграции ID используется карта
миграции. Файл содержит конфигурацию того же сервера, которая уже хранится в профилях.

Оба размера интерфейса показывают активный сервер из этого снимка. Если запись была потеряна
ещё до исправления и восстановить её достоверно нельзя, выводится «Активный · нет в списке»;
вместо первого запуска остаётся статистика работающего сеанса. Выбранный сервер не выдаётся за активный.

Файлы: `desktop/.../DesktopModel.kt`, `desktop/.../App.kt`, `logic/.../model/ActiveConnection.kt`.

### 2. Обновление баз и настроек не заменяет активный сервер выбранным — P1

До исправления эти пути вызывали `connectSelected()`. После ротации подписки это могло
подключить другие реквизиты без явного выбора пользователя. Теперь переподключается сохранённая
активная конфигурация; если она неизвестна, приложение просит явно выбрать сервер.
Удаление подписки также определяет её активность по сохранённому серверу.

Файл: `desktop/.../DesktopModel.kt`.

### 3. Отклонённая горячая смена сохраняет результат проверки прежнего соединения — P2

Исток: `e8177a4`. Результат проверки сбрасывался в `Checking` до подтверждения смены сервером.
Для backend без отдельной периодической проверки и при прежнем статусе он мог не восстановиться.
Теперь новая проверка начинается при подтверждённом изменении соединения, а отправка команды
отражается отдельным уже существующим признаком `switching`.

Файл: `desktop/.../DesktopModel.kt`.

### 4. Местоположение меняется только для подтверждённого подключённого сервера — P1

Исток: `bec8c76`. Отложенный callback от connected-кадра мог получить блокировку уже после
отключения и повторно применить режим местоположения: проверялась опция, но не состояние службы.
Кроме того, страна менялась при отправке горячей смены, до её принятия worker, включая отказ.

Теперь перед применением требуется `state=connected`. Страна передаётся внутри статуса worker
и меняется вместе с подтверждённым outbound. Поле ответа совместимо с существующим клиентом;
формат запросов не меняется.

Файлы: `service/main_shared.go`, `service/config.go`.

## Обнаружено и остаётся неисправленным

Следующие пункты — конкретные дефекты исходников 1.0.0. Они не воспроизводились изменением
рабочих сетевых настроек этой машины. Локальный патч выше не является исправлением этих пунктов.

### 5. Первый запуск Linux/macOS не устанавливает службу из интерфейса — P1

Новый Unix-backend возвращает `unavailable/service_missing`, если сокета нет.
`ControlTile` запрещает подключение при `unavailable`, а `ConnectionProblem` показывает действие
ремонта только для Windows-кода `service_denied`. Других вызовов `repairService()` из сценария
первого подключения нет. Пакеты, согласно текущей сборке, сами службу не регистрируют.
Поэтому обещанное в README первое подключение с запросом пароля недоступно из обычного интерфейса.

Места: `desktop/.../App.kt` (`ConnectionProblem`, `ControlTile`),
`platform/.../DesktopPlatform.kt` (`UnixTunnelBackend`, `repairService`). Исток: `bec8c76`.

### 6. Kill switch macOS блокирует разрешённый трафик и теряется при замене фильтра — P1

В `service/firewall/blocker_darwin.go:74` стоит `block drop out quick all` раньше всех
разрешений. При совпадении `quick` обработка прекращается, поэтому следующие разрешения
для utun, root и DHCP не достигаются. Аналогичная проблема есть у входящих правил.
Семантика сверена с [документацией PF](https://www.openbsd.org/faq/pf/filter.html).

Отдельно `Close()` в строке 107 очищает общий anchor даже тогда, когда счётчик активных
экземпляров остаётся ненулевым. Сценарий «поставить новый фильтр, закрыть старый» стирает правила
нового фильтра. Для исправления нужны корректный порядок правил, владение anchor и проверка
на настоящем macOS; простой перестановки двух строк недостаточно.

Исток: `bec8c76`.

### 7. Аварийное восстановление Unix kill switch отсутствует в пути запуска — P1

`CleanupLeftovers()` определена в Linux/macOS-реализациях firewall, но нигде не вызывается.
`runDaemon()` восстанавливает местоположение и запускает IPC, не убирая оставшиеся правила.
После аварии старые nftables-таблицы могут продолжать запрещать сеть независимо от нового
экземпляра службы и его команды отключения.

Дополнительно `blocker_linux.go:53` разрешает в output любой `ct state established,related`
без привязки к интерфейсу или владельцу. Ранее установленные прямые соединения остаются
разрешены после включения kill switch. Это расходится с заявлением о блокировке всего обходного трафика.

Исток: `bec8c76`. Реальные правила nftables в этой проверке не устанавливались.

### 8. DNS macOS/Unix не гарантированно возвращается после ошибки или аварии — P1

- `worker_dns_darwin.go:44` считает каждое слово вывода `networksetup -getdnsservers` адресом.
  Ответ о том, что явных DNS-серверов нет, затем передаётся обратно как список серверов,
  вместо специального значения `Empty`.
- В `worker_unix.go:87` восстановление ставится в `defer` только после полностью успешного
  `applySystemDNS()`. Ошибка на одном сетевом сервисе после изменения предыдущих оставляет их изменёнными.
- macOS-backup хранится только в памяти worker. При принудительном завершении worker `defer`
  не выполняется, а у нового процесса нет данных для восстановления. Linux-backup файла есть,
  но путь запуска службы его не восстанавливает; после аварии DNS может указывать на исчезнувший TUN.

Исток: `bec8c76`. Нужны сохранение исходного состояния до изменения, откат частичного применения
и восстановление при следующем запуске службы.

### 9. Режим местоположения не сохраняет точное исходное состояние политик — P1

Windows сохраняет только факт наличия `DisableLocation`, затем записывает обе политики в `1`.
`clearLocationPolicy(had=true)` ничего не восстанавливает. Например, исходный DWORD `0`
остаётся равен `1` после отключения VPN; исходное состояние второй политики не фиксируется вообще.

Unix сохраняет `SourcesWereRunning`, но `restoreServerLocation()` безусловно вызывает
`restoreLocationSources()`: ранее остановленный или отключённый источник геолокации
включается после отключения VPN. Это отдельные ошибки от исправленной выше гонки.

Места: `service/system_windows.go:65`, `service/system_windows.go:89`,
`service/system_unix.go:162`. Исток: `bec8c76`. Режим по умолчанию выключен.
